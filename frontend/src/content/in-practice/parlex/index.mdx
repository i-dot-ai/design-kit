## The problem

Parlex helps civil servants and parliamentary staff research UK Parliament: debates, written questions, committees and members.

People paste Parlex answers into briefings. So the worst thing Parlex can do isn't to look dated. It's to give an answer that's out of date or impossible to check, which people trust anyway.

We wanted to know 2 things:

- what Parlex looks and feels like when the Design Kit decides the visual language
- how quickly we can then improve it, one change at a time

## What we did

We rebuilt Parlex as a clickable prototype using the kit's prototype skill: one HTML file that anyone can open. Then we made one change at a time, and saved each version.

## The kit in practice

### What the kit gave us

Kit components covered almost every part of the screen, so we spent our time on the product, not on buttons and spacing.

Where the kit's guidance and the brief disagreed, the kit won. In 5 places it changed what the brief asked for. For example, Send is never disabled: sending an empty message shows an error instead. And New chat is a secondary button, because Send is the primary action.

### Where we built our own

Parlex is chat-shaped, and the kit had nothing for some parts of a chat product. We built these with kit tokens and spacing:

- an app shell, with a sidebar and a message box pinned to the bottom
- research steps that show an AI working through a task
- an actions menu for each chat
- drag and drop, always with a non-drag alternative

Each one is a candidate to add to the kit, so the next chat product doesn't have to build it again.

### Where we departed

We left out the GOV.UK footer. The message box is pinned to the bottom of the screen, so a footer would sit under it, and people would only find it by scrolling past the conversation. We recorded this as a deliberate departure, with what it means for the links the footer normally holds.

## What we learned

- **Reskin first, then change one thing at a time.** Keeping the visual rebuild apart from UX changes made each decision easy to review.
- **Use the kit to settle disagreements with the brief.** Write down each one, so the product team can confirm it.
- **Choose the brand by audience, not by phase.** A prototype should look like the product it's testing, or research tells you about the wrong product.
- **Chat products find the same gaps.** Feed them back to the kit.

## What's next

We haven't tested these changes with users yet. Next, we want to find out:

- whether people check the sources and search terms when an answer looks wrong
- whether pasted answers keep enough source information for a briefing
- whether hiding the classification behind a link is safe, which needs product sign-off
